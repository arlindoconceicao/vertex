# Platform Privacy and Verification (SSIaaS)

The SSIaaS platform was designed upon the pillars of **Self-Sovereign Identity (SSI)** and **Data Minimization**. This document describes the implemented privacy policies, especially related to the lifecycle of generated PDFs and the deletion of Personally Identifiable Information (PII).

## 1. Zero Permanent Knowledge of PII
The platform operates solely as a conduit between the Issuer and the Holder.

1. During the request phase (**PENDING**), the platform stores the PII (JSON `vcPayload`) provisionally, only for display until the Issuer completes the signature in the mobile application.
2. When the PDF (signed and encrypted via ML-KEM) is uploaded to the platform, it is temporarily stored alongside the original PII so the Issuer can review the issued data.
3. **Automatic Deletion**: As soon as the Holder downloads the encrypted PDF (whether via Web or Mobile App), the API registers the download date (`pdfDownloadedAt`), immediately extracts, and permanently replaces all sensitive PII with a **Metadata Summary (Identifiers)**.
4. The database then uniquely stores:
   - Issuer's DID
   - Holder's DID
   - Signature Timestamp
   - Schema ID
   - Plaintext PDF Hash (SHA-256)

Thus, in the event of a platform breach, no personal data of citizens/entities will be exposed in the database.

## 2. PDF Retention Configuration
Since the stored PDFs are doubly protected (AES-256-GCM + ML-KEM of the recipient's public key), they remain secure in the cloud database. However, for strict retention policies and disk savings, we introduced the **Layered Retention Control**.

- The **Issuer** can configure, in the "Platform" tab within Settings, the number of days a PDF will remain available for download (between **1 and 15 days**).
- The default is 7 days.

The execution of this retention works in 3 complementary security layers:
1. **Logical Expiration (Real-Time):** When the recipient attempts to download the PDF, the API and Interface immediately calculate if `pdfDownloadedAt + pdfRetentionDays` is less than the current date. If so, the interface hides the download button and the API blocks the download with an `HTTP 410 Gone` error, ensuring absolute privacy even if physical deletion in the database hasn't occurred yet.
2. **Dynamic Cleanup (Dashboard):** Every time an issuer accesses their main Dashboard screen, the platform silently executes a physical deletion of all PDFs generated by them that have exceeded their individual preference.
3. **Absolute Global Cleanup (Cronjob):** A daily Cronjob (configured via `vercel.json` and `/api/cron/cleanup-pdfs`) acts as a "global garbage collector", sweeping and physically deleting any PDF from the server that has exceeded the platform's maximum limit (**15 days**), regardless of the user's individual settings, ensuring the cloud does not become an infinite repository.

## 3. Verification by Proof of Existence (via Hash)
An essential pillar of decentralized identity is the ability of a third party to validate a credential.

Usually, the W3C requires the JSON to be validated on its signature structure (`proof`). However, in the **Secure PDF Credential** model, what attests the possession of the plaintext data is the SHA-256 Hash.

### How it works:
1. The holder extracts and reads their local PDF (decrypted by the Mobile App).
2. The holder sends this PDF offline to the Verifier (Third Party).
3. The Verifier (or the platform itself, using the `lib/get-pdf-hash.js` script) generates the plaintext SHA-256 Hash of this PDF.
4. On the public `/verify` screen of the platform, the Verifier selects the **"PDF Hash (Proof of Existence)"** tab and pastes the SHA-256 code.
5. The SSIaaS platform responds affirmatively, informing the DID of the issuer, the schema used, and when it was signed (retrieving the metadata from the database, binding the validity of the file).
